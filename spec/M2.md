## Done — item 7 (keyword spotting, source separation, spoken language ID) ✅ (2026-07-10)

All three shipped as full vertical slices (engine → command → catalog → descriptor `implemented: true` → bench page → persisted runs → fixture + `--ignored` tests). Engine layer verified against **real models** in `fixtures_integration.rs` (green under plain `cargo test`); playground pages not yet exercised live.

**Keyword spotting (`kws`)** — catalog `kws/kws-zipformer-gigaspeech` (17 MB, EN). `engines/kws.rs` wraps sherpa's `KeywordSpotter` (encoder/decoder/joiner + tokens.txt). `kws_pipeline_start` (live mic, new `start_kws_pipeline` in `pipeline/mod.rs` + `PipelineEvent::KeywordHit {keyword, startTime}`) and `kws_analyze_file` (chunk-fed offline). Param `keywordsScore`. Page `kws-tool.tsx`: tokenized-keyword editor with **saved lists** (`~/.vocalis/playground/kws/lists.json`, zod-validated), "Load model defaults", live detection log, file mode with hits marked on the Waveform.
- ⚠️ **Caveat (keyword tokenization):** sherpa's C/Rust API does **not** tokenize plain text at runtime — the `KeywordSpotter` requires **pre-tokenized BPE** keywords (e.g. `▁HE LL O ▁WORLD`), supplied via `keywords_buf` (custom) or `keywords_file` (empty list → the model's bundled `keywords.txt`). The plan's "type any plain keyword" assumption was wrong. The tool seeds from bundled defaults and documents that custom keywords need `sherpa-onnx-cli text2token` (a Python-only utility). Runtime plain-text tokenization would need a sentencepiece dependency (deferred). Positive detection verified: keyword `▁ L IGHT ▁UP` fires "LIGHT UP" on the model's `test_wavs/0.wav`.
- Keywords must be present at **spotter creation** (config `keywords_buf`/`keywords_file`), not only per-stream — `create_stream_with_keywords` alone fails sherpa's config validation.

**Source separation (`separation`)** — catalog `separation/spleeter-2stems-fp16` (35 MB). `engines/separation.rs` binds the C API via **raw FFI** — sherpa-onnx 1.13.4's Rust crate does not wrap source separation, but the symbols are in the linked `sherpa-onnx-c-api` static lib (spec §7.2). `separate_file` caches the engine in `SpeechState`, writes stems to `~/.vocalis/playground/separation/runs/<stamp>/<name>.wav`. Page `separation-tool.tsx`: file-input only, per-stem Waveform with exclusive play (solo, no mixer), export to `~/.vocalis/exports/`.
- ⚠️ **Caveat (stereo):** Spleeter rejects mono input — the mono clip is fed as two identical channels; multi-channel output stems are downmixed to mono for preview/export. Struct layout mirrors `c-api.h` @ v1.13.4; FFI verified by linking + a real-model fixture test (2 non-silent stems).

**Spoken language ID (`langId`)** — catalog `lang-id/whisper-tiny-langid` (116 MB, multilingual). `engines/langid.rs` wraps sherpa's `SpokenLanguageIdentification` (whisper encoder/decoder). `langid_file` caches in `SpeechState`. Page `langid-tool.tsx`: mic/file/library input, ISO→friendly-name map, recent runs.
- ⚠️ **Caveat (single language):** the sherpa API returns only the **top language** — no per-language scores are exposed, so the page shows one detection, not the spec's top-5 table (confidences are not faked). Verified: English fixture → `en`.

## Remaining work

### 9. API engine adapters — original plan (for reference)

All adapters live in `src/lib/engines/` (`openai.ts`, `groq.ts`, `elevenlabs.ts`, `deepgram.ts`) and implement the same TS `EnginePort` shape per task (`transcribe`, `transcribeStream`, `synthesize`, `diarize`) so bench pages and pipelines never branch on kind (spec §3.4).

- **Order of work:** batch first — OpenAI STT (`/v1/audio/transcriptions`, whisper/gpt-4o-transcribe), Groq STT (whisper-large-v3, OpenAI-compatible endpoint), ElevenLabs STT (Scribe) and TTS, OpenAI TTS. Then Deepgram: batch (prerecorded) + diarization; streaming (WebSocket) last.
- **File access:** adapters need bytes to upload; read the wav through a Tauri fs command (file-based operations may pass through IPC — the "no raw audio over IPC" rule is about realtime capture). Keep uploads streaming/chunked where the SDK allows.
- **Deepgram streaming:** realtime mic → cloud is the one case where audio must leave Rust. v1 approach: capture with `getUserMedia` in the webview and feed the Deepgram WS directly from TS — the audio is explicitly leaving the device, the engine chip shows `☁ deepgram`, and privacy mode blocks it entirely. Do **not** route API-bound realtime audio through the Rust pipeline. If this proves flaky, defer streaming to M3 and note it — batch adapters are the M2 exit requirement ("local-vs-API comparable on ASR/TTS pages").
- **Eligibility, not fallback:** flip each descriptor's `implemented: true` only when its adapter works; the router already handles `no-key`/`privacy` disabling. **Never add a silent local→API (or API→local) fallback** — an API failure surfaces as an error in the results panel.
- Keys come from the keychain via the settings store; ElevenLabs/OpenAI quirks from Sapio apply (omit empty optional params; TTS responses are raw bytes — see `inspiration.md` §8).
- Tests: adapter unit tests with mocked `fetch` (request shape + error mapping); no live-API tests in CI.
